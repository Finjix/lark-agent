# Publish a requirement (发布需求)

The user gives requirement documents; a CLS ticket asks a supplier to make the materials. The whole task: append the progress-sheet rows → verify → CSV → unpublished CLS draft → import the CSV into it → screenshots of the progress sheet and the draft → copyable group message. Publishing the draft and sending the message are the user's.

Finished material files to put into CLS are [upload.md](upload.md), not this workflow. Logins, approval, steps on request, files and how to talk to the user are in [SKILL.md](../SKILL.md).

Common partial tasks: **only the CSV** ("只要 CSV"); **numbers first** ("帮我占 15 条编号", no document yet): rows only (a request without `cls` and `script_url`), and later **the ticket for those rows** ("发单", §5); **writing into the requirement document** ("把需求填到文档里", §6). Again on request: screenshots, the group message, the CSV, a read-back of the draft.

**Several links in one message are one request:** one plan, one approval, one append of all rows, one CLS draft per document, one group message for all.

The CSV stays in the batch directory: never copy, link or mention it, unless the user asked for the CSV itself; then copy that group's CSV to the working directory and link it.

## 1. Work out the request and plan

Run `gof feishu doctor` once (bridge, user, scopes); a missing permission goes to the user. Commands: [feishu-commands.md](feishu-commands.md), [cls.md](cls.md); files: [data-contract.md](data-contract.md).

The user gives one or more Feishu requirement links (a sheet tab or a doc, usually one per supplier); without a link, ask for it. The user says there is none (没有文档): the group's `script_url` is `无`, which is what its CSV's 脚本内容 says. Only numbers reserved for now: plan rows only (no `cls`, no `script_url`); the plan shows numbers and names and no CLS part, the ticket comes later (§5). Each link is its own group, in the order given.

Gather:
1. `gof feishu document --url <link>` per link: `title` (usually names the supplier: 杨燃对接文档, 丁杰AI), wiki `path`, and the tab (the linked one, else the newest: `sheet.chosen_by`) with header and rows, or the doc text. `--full` reads whole scripts.
2. `gof feishu snapshot --output <tmp>/<new>.xlsx`, then `gof feishu context --snapshot <it>`: target sheet, `next_number`, `naming` and the dropdown `options` of 一级标签 / 二级标签 / 创意形式 / 设计师供应商 / 创意者脚本审核人.
3. `gof cls catalog --output <tmp>/catalog.json`: CLS account, permissions and `choices` (GOFCN directions, task types, suppliers, people).

Fields (the first source that answers wins):
- **条数 (quantity):** a sheet tab: one per requirement row (rows with a brief or script). A doc: what the newest dated entry, or the one the user names, asks for ("产出44条"). A count in the user's message wins.
- **设计师供应商** (required, one per document): the message or the doc, else the doc title, spelled as in `options`. Nothing names one: ask (with the other open points); never leave it empty on your own. Only when the user says it is not decided yet ("供应商待定"): leave `supplier` empty; the sheet cell stays empty, CLS takes `待定供应商` and the group message says `供应商：待定供应商`. When the supplier is also the 创意者脚本审核人, still give `supplier` as that person: the sheet cell stays empty (`supplier_cell_empty` in the plan; say so in the plan), while the group message names the person, and so does CLS when the person is one of its suppliers (`choices.suppliers` holds only outsource accounts). When the preview cannot match them, ask which CLS supplier the ticket gets (a `choices.suppliers` name, or `待定供应商`) and give it as `cls.supplier`. Within one request every document's cell is filled or none is (otherwise two requests).
- **一级标签 / 二级标签**, per row: tags or naming stated in the message or doc ("标签：多明星04_2min") first; otherwise judge from the row's script and other columns which existing option fits best (direction, selling point or theme). The doc's column labels are hints, not a mapping. Ask only when there is no script or two options fit equally. Rows that differ are separate `items`, in doc order. A tag is one part of the name and never holds `_`.
- **创意形式** (制作形式, optional): only what the message or doc states for the rows (a 创意形式 column, "3D 制作", a name that holds it); never guessed from the script; otherwise empty. Filled for all rows of the request or for none; when only some rows state it, leave it empty for all and put it in front of their 提炼词 (`3D_围炉`), which gives the same name.
- **提炼词** (`keyword`, the end of the name; usually different for every row unless it is `关键词`): what the message or doc states, for all rows or for each (a 提炼词 / 关键字 column, a naming rule: "命名加入关键字【ZJJC】" → ZJJC). Otherwise find the pattern by which the doc names each material and take the part that tells them apart: a heading per piece like `GOFCN56890 企鹅保龄球 V15` → 企鹅保龄球 (not the number of the material it builds on, not the version), a title / 名称 / 主题 column, the names of delivered files. Judge from the whole doc, keep the words as the doc writes them, use one rule for all rows of a doc, never make one up; ask about a row the rule does not fit. One with `/` or `\` cannot be used (the name is also the creative's CLS name): ask how to write it. A variant listed under a piece (同一条的国风配乐备用版) is another row of that piece, with its own 提炼词 unless the doc names it. Rows with different 提炼词 are separate `items` of `quantity` 1, in doc order. Only when the doc names none: `关键词`, which the user confirms unless they already said so.
- **合并变体名称** (merge variant names; off unless the user turns it on): variants are materials of one piece with the same tags (and 创意形式) and the same first part of the 提炼词 but different endings (`原生家庭WM_剧情衔接_割资源冰块对抗_竖版`, `原生家庭WM_剧情衔接_剧情叙事_竖版`), or listed under one piece; a first part that extends another one of this request is a variant too (`得加钱WM熔炉版` of `得加钱WM`). When the docs have variants and the user has not said, ask once (with the other open points, else in the plan); no answer means not merged. Merged: one row per piece, 提炼词 = the shorter first part (`GOFCN67747_AI剧情_短剧表达_原生家庭WM`); the sheet, the CSV and the CLS ticket have one line per piece, and the delivered files are named `<素材名称>_<变体>`.
- **创意者脚本审核人** (`reviewer`): the message or doc; else a name in the wiki `path` (张天伟) or initials in the title (…-TW → 张天伟), when it matches exactly one `reviewer` option or CLS person; the plan says where it came from. The reviewer is also the CLS creator and the message's 创意人.
- **CLS 创意方向 / 任务类型** (`cls.direction`, `cls.task_type`): stated, else the best fit in `choices` (混剪 → 2D剪辑 / 视频; AI video → AI视频 / AI生成).
- **CLS 供应商 / 创意人:** the program matches the supplier and reviewer to CLS names; if the preview cannot, set `cls.supplier` / `cls.creator` to the `choices` name that is clearly the same.
- **脚本内容** (`script_url`): the user's link as given; `无` when the user says there is no document.
- **`label`** (optional): the short name the user or doc gives the requirement ("迭代", "素人剧情"); the plan shows it as `message_kind` ("素人剧情*25"), where the user can correct it.
- **Dropdown values:** prefer an existing option that means the same (spelled as in `options`). 一级 / 二级标签: add a new one only when the message or doc states it. 创意形式, 设计师供应商, 创意者脚本审核人: a value the dropdown lacks is added. Either way the plan lists it (`new_options`) and the go-ahead covers it.

Fixed by the program, never asked and never put in `request.json`: the CLS requirement name (`GOFCN<first>-GOFCN<last>` from the real numbers), the material numbers (continuing the sheet, running on across groups in link order), the material name (`naming`, written by the plan's formula; a row may give the name it must get as `material_name` when the doc names its rows, and the plan checks it comes out exactly), the CSV tag `玩法卖点（单选，必选）/展示向/展示向`. One document is one group (one CSV, one CLS ticket); documents are never merged. Other progress fields (客户端, 创意表达, 创意批次, 参考 …) stay blank. Quote and currency default to CLS's 0 / cny. Sheet: the one the user names, else the newest year-month GOFCN sheet; if `plan` reports a tie or an unusable header, ask.

Collect all open points and ask them **once**, in one short message at the end of the turn: only the missing information, no plan preview. A 提炼词 the doc does not give is one of them (whether these N rows take `关键词`); when it is the only one, ask it in the plan instead. The same goes for the merge question.

Then:
1. Write `<tmp>/request.json` ([data-contract.md](data-contract.md)); run `gof feishu plan --request … --snapshot … --output <tmp>/plan-<time>.json` and `gof cls --preview --request … --catalog …`. A refusal: fix the request, or ask when it shows something cannot be worked out.
2. Show the plan in plain language, about 6-10 lines for one document (with several: the shared lines once, then 3-4 lines each):
   - the tab read (if the link named none), the progress sheet, the row count and the expected numbers;
   - the **full 素材名称** with the expected number, exactly as the plan names it (never split into number and name, never shortened): rows of one name by count with the first and last ("12 条：GOFCN67680_AI生成_设定3.0_关键词 – GOFCN67691_AI生成_设定3.0_关键词"); rows with 提炼词 of their own one per line when few, with the rule they came from and one example; merged rows the same way, with nothing about their variants;
   - for the group's `default_keyword_rows`, unless the user already confirmed: whether these N rows take `关键词`; variants the user has not decided on are planned unmerged, with the question whether to merge them;
   - 供应商 (pending, CLS `待定供应商`, only when the user said so) and 审核人 / 创意人, 创意形式 when filled, dropdown values to add (`new_options`);
   - per CLS group: requirement name, 创意方向, 任务类型, CLS 供应商, quantity and script link; that the draft is saved unpublished with the scripts imported; the group message's `message_kind` (the 需求编号 is filled in after publishing);
   - any `same_name_rows` (rows already in the sheet under a name the request gives, most likely registered before: leave them out unless the user says they are new). When every row is in the sheet already (all `same_name_rows`, or the document names its rows with numbers the sheet has), nothing is appended: give those rows their ticket (§5).
   
   End by saying you will start once they confirm. A correction: plan again and show it again.

## 2. Execute: append and CSV

1. `gof login check`.
2. Each `new_options` entry: `gof feishu dropdown-add --field primary|secondary|form|supplier|reviewer --option <value> --sheet <sheet name>` (safe to re-run; see [feishu-commands.md](feishu-commands.md)).
3. A fresh `gof feishu snapshot`, then `gof feishu prepare --plan <tmp>/plan-….json --snapshot <fresh>.xlsx` (creates the batch). If rows, numbers or names changed (colleagues appended meanwhile), show the updated plan and wait.
4. `gof feishu append --batch …`: one write of the approved range, a full re-export and the verification; success records `append_verified`. `foreign_changes` lists colleagues' edits elsewhere in the workbook: they do not concern the append; mention them only if asked. A refusal **without** `write_sent` came before anything was sent: snapshot and `prepare` again. A refusal **with** `write_sent: true` means the rows may be in the sheet: never `prepare` or append that request again; go to step 5.
5. Interrupted, `write_sent` or unclear: `gof batch status`, then `gof feishu reconcile --batch …` ([Interruption recovery](feishu-commands.md#interruption-recovery)). Complete: continue with the existing CSV. Not applied (nothing of it is in the sheet): tell the user; plan again with their go-ahead. Partial or conflicting: report what exists (`rule_issue` says when the new rows lack their dropdowns). A conflict with `matched_cells` equal to `expected_cells` is someone else's edit in the new rows and can never verify: with the user's go-ahead the rows get their ticket through `gof batch adopt` (§5), which closes this batch. After `blocked`, once the cause is fixed, `gof batch record --step resumed` and continue.

## 3. Execute: the unpublished CLS draft

`gof login check`, then per group, one after another in plan order: save the draft (`status=-2`), import the group's CSV with the reviewer as creator, read back. The command sequence is in [cls.md](cls.md#draft-per-group). An unknown save result: read back (`cls read-draft` / `cls verify`) instead of creating again. If a group fails, report which groups have a ticket and which do not.

## 4. Handover

1. `gof batch message --batch …` builds the group message: hand it over exactly as returned, once for all documents. It has no @ (a pasted @ does not become a mention in Feishu), so introduce it, in the user's language, as: the draft has all scripts imported and is not published; after publishing, paste the message below into the group, @李聪（Cici）, and send. `【发布后补填需求编号】` marks groups without an official number (`missing_numbers`): the user fills it in after publishing. Groups without a ticket are left out (`skipped_groups`): say which. When the user later gives the real number: `gof batch record --step requirement_number`, then build the message again.
2. `gof batch report --batch …` (prints the report with its `links`; no `--output` needed).
3. **Screenshots**, into the working directory: the progress sheet on the appended rows, `gof feishu screenshot --batch … --output <working dir>/progress-<time>.png`, and each group's draft, `gof cls screenshot --batch … --group <group> --output <working dir>/cls-draft-<group>-<time>.png` (`--group` may be left out for a single document). Take what the run produced: no progress picture when nothing was appended, no draft picture for a group without a draft. Open each picture yourself before it goes out: a sign-in page, a "no permission" page, an empty sheet or one that does not show the new GOFCN numbers is not handed over. A refused or poor picture never fails the task: say in one line which picture is missing and why (the command's `reason`: a lapsed Feishu web login means `gof login check`, then once more; a page that did not open, not a lapsed login, means once more a little later), and keep the links.
4. Give the user: the appended numbers; the links from the report's `links`, only those ("创意进度表：<link>", "CLS 草稿：<link>", with several documents "CLS 草稿（<供应商>·<类型名>）：<link>"); the copyable message; what is left for them (publish, fill in the 需求编号, paste into the group, @李聪（Cici）, send).

## 5. A ticket for rows already appended (占号 first, 发单 later)

When the user asks to 发单 / 建单 for rows that are in the progress sheet without a ticket (numbers reserved earlier, an earlier conversation that broke off after the append, rows someone registered by hand), the rows are not appended again: the ticket is attached to their batch.

1. The batch: the one this session made; else `gof batch list --number <a material number>` (`ticket: false` = no ticket yet). None found (registered elsewhere, or the batch was removed after the retention period), or the batch is stuck in a conflict that is someone else's edit (§2 step 5): take the rows over as the sheet has them, with a fresh `gof feishu snapshot` and `gof batch adopt --numbers <first>-<last> --snapshot <it> --supplier <…> --reviewer <…>` (as in §1; left out, the rows' own). It writes nothing to the sheet and gives the batch to continue with. One ticket is one run of numbers: rows with a gap between them are taken over run by run. A refusal names the number the sheet lacks or the rows that differ: tell the user.
2. Work out as in §1: the requirement document (`script_url`, or `无`), CLS 创意方向 / 任务类型 (and `cls.supplier` / `cls.creator` if the preview cannot match them), `label` if given. `gof cls catalog`, write `<tmp>/ticket-<group>.json` (`{"script_url": …, "cls": {…}, "label": …}`) and run `gof batch ticket --batch B --group 01 --ticket … --catalog … --preview`.
3. Show the plan from the preview (requirement name, quantity, first and last name, 创意方向, 任务类型, CLS 供应商, 创意人, 脚本内容, saved unpublished with the scripts imported, `message_kind`), ending by saying you will start once they confirm.
4. After the go-ahead: the same command without `--preview` (writes the group's CSV and records the ticket), then §3 for that group and §4 (no progress screenshot: nothing was appended now). A correction before §3 starts: attach again; the last one counts.

## 6. Writing into a requirement document

When the user asks to put the requirement into their document ("把需求填到文档里", "把编号写进需求表"): read it, plan the edit, show it, write after the go-ahead. Only additions: new blocks, or text in empty cells; nothing in the document is changed or deleted. Edit files: [feishu-commands.md](feishu-commands.md#editing-a-requirement-document).

1. Docx: `gof feishu document --url <link> --outline` (top-level blocks by `index`, a table by its first rows; `--block <index>` for one whole). Sheet: `gof feishu document --url …` (rows by sheet row, columns by letter).
2. Follow the document's own layout: a dated log gets the new entry where the newest one is (usually at the top), headed and laid out like the entry before it (the same heading level and title pattern, "需求数量：N条", a table with that entry's header and the names in the 命名 column); a table with an empty 命名 column gets the names filled in. Write the edit file (`insert` or `fill`) to `<tmp>` and run `gof feishu doc-edit --url … --edit … --check`.
3. Show what will be written where, in a few lines (above which heading, the new heading, the quantity line, the table's columns and row count), wait for the go-ahead, then run it without `--check`. `already_present`: it is there already, nothing was written. A refusal names the cell that is not empty or the place that moved: read again and plan again.
4. After every edit that went in (`doc_updated`, or `already_present` after a write of this task), hand back a picture of it: `gof feishu doc-screenshot --url <link> --output <working dir>/doc-<time>.png`, with `--block <focus.block>` for a docx or `--sheet <focus.sheet_id> --range <focus.range>` for a sheet (from the edit's result). Check it as in §4 (it must show the written text). A refused or poor picture never fails the edit: say in one line why it is missing.
5. A login from before document editing lacks the permission: the command says so; log the user in again (`feishu_login` with `extra_scopes` `docx:document`), then run it again. No edit access to the document: the user asks the document's owner for it.
