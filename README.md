# 飞书 Codex Desktop 任务机器人

Windows x64 本地常驻服务。通过飞书私聊或群聊 @机器人提交任务，在正在运行的 Codex Desktop 中按租户和用户复用固定聊天，保留对话上下文，流式回传过程消息、最终回复和交付文件。

## 直接运行

当前项目目录已经包含 Node.js 24.21.0 LTS、飞书 SDK、SQLite 原生模块、全部 npm 依赖和编译产物，可直接在本机运行，不需要安装系统 Node.js 或执行 npm install。

1. 安装、登录并启动支持版本的 Codex Desktop，至少完成过一个本地聊天。当前验证版本：**26.1007.9446.0**。
2. 在飞书开发者后台配置企业自建应用，启用机器人，按 [飞书配置说明](docs/feishu.md) 开通权限、长连接和消息事件，并发布应用。
3. 复制 `.env.example` 为 `.env`，填入应用凭证和访问范围：`ALLOWED_TENANTS` 对指定企业全员开放，或使用 `ALLOWED_USERS` 逐人配置。项目自带的 `scripts/setup.mjs` 可通过本机表单填写凭证和用户名单。
4. 双击 `doctor.cmd` 检查运行时、SQLite、Desktop 上下文及飞书凭证。
5. 双击 `start.cmd`。日志出现“飞书长连接已启动”后即可使用。

启动不下载依赖。实际飞书通信、模型任务和 Desktop 登录仍需要网络。服务须运行在与 Desktop 相同的 Windows 用户环境中。

## 使用

私聊直接输入任务；群聊需要 @机器人。支持文字、图片、文件及图文混排消息；例如把图片和“改成卡通风格”放在同一条消息中发送。每条消息最多 10 个附件，单个附件限 30 MB。单独发送附件时，默认先查看和说明附件内容。暂不支持的消息类型或附件下载失败会明确回复原因。

用户文字原样作为 Codex 用户输入发送，保留空格和换行，不拼接任务编号、交付说明或附件路径。群聊只移除用于路由的机器人 @标识；图文消息按标题和文本行还原。交付要求和附件清单通过独立的应用上下文传入，图片另用原生图片输入。只发送附件时，用户文字保持为空。新用户首次建立会话时会执行一次简短初始化，初始化回复不会回传飞书，之后包括首条业务请求都通过原文通道提交。

任务关联使用持久化的客户端请求 ID 和 Desktop 轮次 ID，同一用户连续发送相同原文也分别执行、分别回传。流式正文、交互请求、生成图片及文件交付仍走原有回传队列；提交响应丢失时核对原轮次，不自动重发用户请求。升级前已提交的任务继续支持原任务标记恢复。

会话自动使用发送者的飞书显示名命名，格式为 `用户名_yyyy_MMdd_HHmm_ssSS`。时间取会话首次创建时的北京时间，末四位为“秒 + 百分之一秒”，例如 `薯薯_2026_1015_1958_1234` 表示 19:58:12.34；后续消息和服务重启均保留这个时间。需开通并发布应用身份权限 `contact:contact.base:readonly` 和 `contact:user.base:readonly`，同时确保对应用户在应用可见范围内。权限或姓名暂不可用时保留现有名称，任务正常执行；补齐权限后会自动尝试更新已有会话。只保存显示名和会话标题，不保存其他用户资料。

| 指令 | 用途 |
|---|---|
| `/whoami` | 获取本人的 Open ID 和企业租户标识 |
| `/help` | 帮助 |
| `/tasks` | 最近十个本人任务 |
| `/status 任务ID` | 查询状态和结果 |
| `/cancel 任务ID` | 取消排队任务，或请求中断执行 |
| `/approve 任务ID 请求ID` | 仅同意当前授权请求 |
| `/deny 任务ID 请求ID` | 拒绝当前请求 |
| `/answer 任务ID 请求ID 回答` | 回答补充问题；多问题用问题 ID 到回答的 JSON 对象 |

任务调度不设全局并发数量上限，所有具备执行条件的用户任务都会直接启动。`MAX_CONCURRENT_TASKS` 和 `MAX_TASKS_PER_USER` 配置已移除，旧环境中即使保留也不生效。同一租户下每个用户固定使用一个 Codex 会话，消息按 FIFO 串行执行；服务重启后继续复用。`UNKNOWN` 和等待确认只阻塞所属用户会话及冲突资源，不会占用全局名额。配置的共享资源互斥仍生效。查询、取消和交互仅限任务本人或管理员，且不得跨租户。

访问范围在 `.env` 配置。`ALLOWED_TENANTS` 填入企业租户标识（多个用逗号分隔）后，该企业内用户无需逐人登记，私聊和群聊 @机器人均可提交任务；其他企业的用户及管理员均不能越过租户限制。未配置企业时，继续使用 `ALLOWED_USERS` 和 `ADMIN_USERS` 的逐人名单。三项均为空时不允许执行任务。`ALLOWED_CHATS` 仍可额外限制会话，留空则不限制。修改后重启服务。

可向机器人发送 `/whoami` 获取租户和 Open ID。企业全员开放只改变机器人本地准入规则，飞书应用自身的可用范围仍需包含目标成员。

## 项目内依赖和数据

新用户或尚未绑定 Desktop 聊天时自动新建会话；原聊天已归档或已不存在时，下次消息自动建立新会话并重新命名，保留旧会话和任务记录。可用的现有聊天继续复用。尚未提交的消息可在新会话恢复；提交结果不明的消息仍核对原轮次，不重复发送。

- `runtime/node`：官方 Node.js 运行时及 npm，仅由项目脚本调用。
- `node_modules`：精确锁定的项目依赖，含 Windows SQLite 二进制。
- `dist`：预编译 JavaScript；`src`：TypeScript 源码。
- `data`：数据库、控制令牌及保留的飞书审核草稿；后台运行日志在 `data/logs`。
- `data/inputs/任务ID`：按任务隔离保存的入站附件，下载完成后才提交给 Desktop，按任务文件保留期清理。
- `.env`：本机凭证及授权名单，不进入 Git 或离线包。
- 每用户会话目录由 Desktop 原生创建并返回，通常位于“文档/Codex/日期/lark-会话ID/outputs”。每条消息的交付文件保存在其中的 `tasks/任务ID`，实际路径保存在任务记录中。启用此功能后的第一条消息建立固定会话，旧版已经分散的聊天不会自动合并。

Codex 开始工作后，在卡片的绿色标题栏显示“番薯搬砖中...... 12s”，计时从任务开始执行时计算；即使暂时没有新正文，也会持续刷新秒数。公开过程消息和回复正文在卡片正文区域继续流式更新，结束后移除工作标题栏和计时，不展示任务编号、耗时标签、查询提示或内部工具状态。排队时不发工作状态，等待确认或连接核对时也不显示搬砖中。飞书底层使用 CardKit，默认每秒合并更新一次；超过九分钟切换为普通完整内容更新。任务详情可通过 `/tasks`、`/status` 主动查询；授权、补充问题、错误和中断仍会明确提示。

普通文本回复超长时生成 Markdown 附件。普通文件仅上传最终回复明确链接、且真实路径位于所属任务目录内的文件；单个附件限 30 MB。Codex 原生生成图片会按当前轮次单独收集，即使最终文字没有图片链接，也会复制到本次交付目录并作为飞书图片发送；超过 10 MB 时改发文件附件。生成图片记录、上传标识和发送结果会持久化，服务重启后可继续投递。原始模型推理、完整命令输出和内部事件不会进入回复。

## 维护与开发

在项目目录使用以下命令，均通过项目自带 Node：

```bat
project.cmd run build
project.cmd test
start.cmd doctor
start.cmd stop
start.cmd backup
start.cmd retry-delivery all
```

`start.cmd stop` 会通过仅限本机、带随机令牌的控制接口安全停止。也可在启动窗口按 Ctrl+C。健康检查：`http://127.0.0.1:8765/health`；就绪检查：`/ready`，配置未齐时返回 503。

当前仅维护本机运行目录，不保留发布包及离线验收副本。仅克隆源码仓库不会自动获得被 Git 忽略的运行时和依赖；重建环境时需准备项目内 Node 和依赖。以后需要离线分发时，可执行 `project.cmd run pack:offline` 生成带校验清单的 ZIP。

登录自启动为可选项：执行 `scripts/autostart.ps1` 安装当前用户的启动快捷方式；加 `-Remove` 卸载。它以隐藏窗口启动监督脚本，异常退出后十秒重启；正常停止不重启。未自动修改 Windows 设置。Desktop 自身也需登录后启动。

数据库启用 WAL，服务重启会核对执行中任务并恢复队列和投递。飞书投递失败不会重跑任务。永久权限错误保留在 outbox 中，修复配置后可执行 `start.cmd retry-delivery 任务ID`（或明确使用 `all`）恢复投递；没有自动重跑 `UNKNOWN` 任务的入口。

默认关闭任务时限；交互请求 24 小时未响应会请求中断。每条消息的输入及交付文件默认保留 30 天，仅在任务终态、全部投递成功、目录所有权检查通过后清理；用户固定会话和任务元数据继续保留，不因某条消息过期而归档。旧版独立任务仍先归档后清理。

## 兼容性与边界

Desktop 桥接使用内部协议，**仅支持已验证版本**。更新后需要重新验收，不应直接扩大 `DESKTOP_SUPPORTED_VERSIONS`。适配器不修改 Desktop 安装文件、配置或聊天数据库；只读元数据用于发现已有有效调用上下文。

原生 `create_thread` 用于一次性会话初始化。业务轮次通过 Desktop 的 `thread-follower-start-turn` 提交，原文、原生图片和附加应用上下文分开传递。创建或提交结果不明时进入 `UNKNOWN` 并等待核对；只有确认业务轮次从未尝试提交时，才允许恢复准备流程。中断结果以匹配轮次的 Desktop 终态为准。

所有任务共享 Desktop 登录账号、系统权限和已连接服务。独立目录用于组织文件，不提供不同用户之间的操作系统权限隔离。请仅对受信任内部用户开放。
