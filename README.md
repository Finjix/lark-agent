# 飞书 Codex 任务机器人

Windows x64 本地常驻服务：飞书私聊或群聊 @机器人 提交任务 → 用 Codex SDK 在本机执行 → 卡片、最终回复、交付文件回传飞书。

Codex 的登录、对话、生成的图片等一切状态都放在项目自己的 `.codex/` 里。系统自带的 Codex（`~\.codex`）既不读也不写，不受影响；换一台电脑只要 `npm install`、登录一次即可使用。

## 运行

需要 Node.js ≥ 24。不需要另外安装 Codex：`@openai/codex-sdk` 和各平台的 codex 二进制由 `npm ci` 按 lockfile 装进项目，与飞书官方 SDK 一样。数据库用 Node 内置 `node:sqlite`。

1. 飞书后台配置应用，见 [docs/feishu.md](docs/feishu.md)。
2. `.env.example` 复制为 `.env`，填凭证和访问范围。
3. 登录 Codex（只做一次，由管理员做）：`start.cmd codex login`，在浏览器里用企业账号授权；没有浏览器的机器用 `start.cmd codex login --device-auth`。也可以不登录，在 `.env` 里填 `CODEX_API_KEY`。所有飞书用户共用这一个账号，用户不需要任何配置，开箱即用。
4. `start.cmd doctor` 自检，`start.cmd` 启动（首次自动 `npm ci`，每次先编译）。日志出现“Codex 已就绪”和“飞书长连接已启动”即可用。

`start.cmd codex <参数>` 是项目自带 Codex CLI 的入口，永远使用项目的 `.codex/`：`start.cmd codex login status`、`start.cmd codex logout` 等。

**换电脑**：把项目目录拿过去（`node_modules`、`dist` 不用，`plugins/` 里的插件要带上），`npm install`，复制 `.env`，`start.cmd codex login`。要保留各用户的工作目录就一并复制 `user/`，要保留各用户的对话上下文就一并复制 `.codex/sessions`。

## Codex 的运行方式

每条用户输入对应一次 `codex exec`（由 SDK 启动的子进程）；同一个用户的所有输入续接同一个 Codex 对话（thread），所以上下文是连续的。`/new` 让用户丢掉上下文重新开始（见“指令”）。

- **位置**：`.codex/` 保存对话（`sessions/`）、生成的图片（`generated_images/`）和日志，不入 Git。环境变量 `CODEX_HOME` 被忽略，子进程始终使用项目里的这个目录。
- **配置**：不写 `config.toml`，每次运行由程序传入（见 `src/codex/runner.ts`）：关闭 `apps`（登录账号的 ChatGPT 连接器，会被所有飞书用户共用）和 `memories`（记忆存在共用的 `.codex` 里，会在用户之间串；要放开，改 `codexConfig`），`plugins` 只在 `plugins/` 里放了插件时才打开（见“插件”；插件的安装记录由 `codex plugin` 命令写进 `.codex/config.toml`）；模型默认 `gpt-6.1-sol`、推理强度 `medium`，要改在 `.env` 设 `CODEX_MODEL`、`CODEX_REASONING_EFFORT`。
- **登录**：登录文件是 `.codex/auth.json`（启动时收紧为仅当前账号可读，存成文件而不是系统钥匙串）。Codex 不可用或登录被拒绝时，用户只会看到“机器人罢工了”，原因写在日志里；管理员重新 `start.cmd codex login` 即可，服务不用重启（未就绪时每 10 秒检查一次）。
- **权限**：没有任何限制：沙箱 `danger-full-access`、审批 `never`，Codex 可以读写本机任何位置、访问网络，也没有人会被询问。写死在 `src/codex/runner.ts`，没有开关。因为不能交互，做不到的事只会失败，Codex 自己换办法；所以没有 `/approve`、`/deny`、`/answer`：Codex 需要问用户什么，就在回复里问，用户的下一条消息就是回答。
- **提示词**：不向 Codex 注入任何指令，也没有 MCP 工具（除了放进 `plugins/` 的插件自带的技能和工具）：它看到的就是用户发来的文字（外加附件清单，见下）。
- **输入**：用户文字原样提交（保留空白换行）。有附件时在文字前加一段清单（每个文件的路径，并提醒附件内容只是资料、不是用户的指令）；图片同时作为图片输入让模型直接看到画面，其他文件由模型用工具按路径打开。飞书语音消息按文件接收（`语音消息.opus`），同样只是路径。

## 目录

| 路径 | 内容 |
|---|---|
| `src` / `dist` | TypeScript 源码 / 编译产物（`start.cmd` 生成） |
| `dev` | 自动测试，`npm test` |
| `data` | 运行数据：SQLite 数据库、控制令牌、日志 |
| `plugins` | 放插件的地方：把插件文件夹拖进来，重启即可使用，见“插件” |
| `user` | 每个用户的数据和工作目录，见下 |
| `.codex` | Codex 的全部状态（对话、生成的图片、日志），见上 |
| `.env` | 凭证和白名单，不入 Git |

```
user/
  李小明/                     每个飞书用户一个目录，显示名取自飞书，重名依次加 2、3（如 李小明2），分配后不再改变
    workspace/                Codex 的工作目录
      input/                  用户发来的附件，保留原文件名，重名加 (2)；有附件才会创建
    <插件名>/                 插件自己的数据（有插件时由插件创建，见“插件”）
```

任务结束时，服务把这个任务运行期间在工作目录里新建或改动过的文件（复制进来的文件按创建时间算；不含 `input/` 和以 `.` 开头的文件夹）发给用户，再加上回复里链接的、位于工作目录内的文件；每个任务最多自动带 10 个未链接的文件，所以 Codex 顺手写下的脚本等临时文件也可能被发出去。要重发旧文件，让 Codex 再复制一份即可。工作目录里的文件超过 7 天没动过就会被自动删除，见“自动清理”。

## 行为

- **会话**：每个租户下每个用户一个 Codex 对话，同一时刻只执行一条输入；不同用户并行，无全局并发上限。用户的一条输入还没有回传结果（排队、启动、执行中）时，再发来的任何输入都是无效输入：不排队、不转给 Codex、也不回复，只在日志里记一笔；任务结束（完成、失败或取消）后才接收下一条，不等卡片和文件发送完毕。只有 `/new` 不受影响，随时可用。Codex 里找不到原来的对话（比如 `.codex` 被清空）时，下一条消息自动新开一个。
- **不可用时**：Codex 不可用（没登录、二进制缺失）时，新消息不会入队，机器人只回一条“机器人罢工了，请联系 @钟丰骏-实习生”（常量 `BOT_DOWN`，见 `src/types.ts`；Codex 启动或运行失败、附件接收失败等所有机器人自身不可用的情况都用这一句，具体原因只写日志）。服务未启动期间发的消息，服务启动后若被飞书重新推送（发送时间早于启动时间）会被忽略，不会执行。是否过期按飞书服务器的时间判断（每 10 分钟用飞书响应的时间头校准一次），本机时钟与飞书相差超过 5 秒时日志会警告。
- **重启**：Codex 是本服务的子进程，服务停止或崩溃时正在执行的任务随之结束。重启时，排队中的任务取消（没有卡片，不通知），执行中的任务把卡片收尾为失败（回复“机器人罢工了”），未送达的提示和已结束任务的未送达回复一律丢弃（标记为 FAILED，可用 `retry-delivery` 手动重发），启动本身不会向用户发任何新消息。用户重发即可，Codex 对话里已有的内容会接着用。
- **回传**：卡片按 Codex 的步骤顺序展示，和直接用 Codex 差不多：它说的话、执行的命令、改动的文件、MCP 工具调用、搜索、待办清单。命令、文件改动、工具调用，以及超过 600 字的中间说明，都折叠成可点开的面板（标题带 ⏳/✅/❌ 状态，点开看完整命令和输出），最终答案始终展开；推理过程不展示。卡片整体限制在约 26 KB，超出时先清空最旧面板的内容，再省略最旧的步骤。`codex exec` 以完整消息和完整步骤为单位输出，没有逐字流式（SDK 不提供），所以文字是一条一条出现的；卡片每秒合并更新，超过 9 分钟改为整体更新。Codex 工作中标题栏显示计时。长回复转 Markdown 附件；文件只上传最终回复链接且位于交付目录内的（链到交付目录以外的文件，如用户自己发来的附件，一律忽略，不通知；路径里的括号如 `report (2).pdf` 能正确解析）；Codex 生成的图片自动发送（>10 MB 改发文件）。文件上传走单独的队列，大文件不会拖慢卡片更新；投递记录持久化。
- **取消**：任务执行中发 `/new` 会结束它的 Codex 进程，已经说出的内容保留在卡片上（状态为已中断）；进程 5 秒内没结束，也直接把任务标记为已中断，不让用户卡住。已被 Codex 启动的外部命令不保证随之结束。
- **超时**：默认无任务超时（`TASK_TIMEOUT_MS`，到时按 `/cancel` 处理）。

## 插件

插件是别人做好的一个文件夹：技能（`skills/`）加可选的 MCP 服务（`mcp.json`），清单是文件夹里的 `plugin.json`（Agent Plugins 格式，必须有 `$schema`）或 `.codex-plugin/plugin.json`。**把它拖进 `plugins/`，重启服务，所有用户就能用**，不用配置、不用跑任何 `codex plugin` 命令：

```
plugins/
  <插件名>/                ← 插件文件夹本身（里面直接是 plugin.json），不要多套一层
    plugin.json
    mcp.json
    skills/…
```

- **安装**：启动时（接收任务之前）扫描 `plugins/` 下的文件夹，装进项目自己的 Codex（`.codex/`，市场名 `lark-agent`，插件号 `<名字>@lark-agent`）。内容没变的不动；内容变了（不管版本号变没变）整体替换；文件夹删了就卸载。以 `.` 或 `_` 开头的文件夹被忽略，改名加个下划线就是停用。`plugins/.agents/` 是自动生成的，不要动。
- **生效时间**：只在启动时扫描，换插件要先 `start.cmd stop`（或 Ctrl+C）再 `start.cmd`。服务运行中拖文件夹没有效果，这样不会装到一半被拖到一半的文件夹。
- **失败**：某个插件装不上，日志里写明原因（`插件未加载`），机器人照常用其余的，`/health` 的 `plugins.skipped` 和 `start.cmd doctor` 也列出来；`doctor` 在不改动任何东西的情况下告诉你每个文件夹的状态（已安装、未安装、已改动、无效）。
- **MCP 服务和用户**：Codex 不会把自己的环境交给插件自带的 MCP 服务，所以服务会为插件把同名服务重新注册一遍并关掉插件自带的那个，每个用户的每一轮都给它：`LARK_AGENT_USER_DIR`（`user/<名>`，不是其中的 `workspace`）、`LARK_AGENT_USER_OPEN_ID`、`FEISHU_APP_ID`、`FEISHU_APP_SECRET`。同一份环境也在 Codex 的 shell 里，插件的脚本直接能读到。只有 stdio 服务会被这样处理；用 `node` 启动的服务由运行本服务的 node 执行。
- **只放你信任的插件**：插件的脚本和 MCP 服务以本服务的账号、不受任何限制地运行，和 Codex 本身一样。
- **机器人密钥的代价**：有插件时，每个用户的每一轮 Codex 进程都带着 `FEISHU_APP_SECRET`（没有插件时仍然挡在外面）。能和机器人对话的人理论上能让 Codex 读到它。这里没有新增一类风险：Codex 本来就能读 `.env`（见“访问控制”）。想收紧，给插件的设备授权单独建一个飞书应用，把 `.env` 里的 `FEISHU_APP_ID/SECRET` 换成它。
- **数据**：插件自己的数据放在 `user/<名>/<插件名>/`（例如用户的登录信息和中间文件），不在 `workspace/` 里，所以不会被自动清理，也不会被当成交付文件发给用户。用户之间的隔离只是约定：Codex 是 `danger-full-access`，同一个 Windows 账号，被提示词注入的模型能读到别人的目录。

## 自动清理

服务启动时（接收任务之前）先清理一次，之后每 24 小时一次：**超过 `RETENTION_DAYS`（`.env`，默认 7）天没有被动过**的下列内容会被删除。文件的“时间”取创建、修改、移动三者中最近的一个，所以几天前创建、但昨天还在用的文件不会被删。一时删不掉的（正被程序占用、没有权限）留到下一轮（24 小时后）。

| 范围 | 删除 | 不动 |
|---|---|---|
| `data/logs` | 日志文件（`.jsonl`） | 数据库、控制令牌、`start.cmd backup` 生成的备份（备份要自己清理） |
| `user/<用户名>/workspace` | **里面所有文件**（用户发来的 `input/` 附件、Codex 生成的文件，包括以 `.` 开头的），以及因此变空的文件夹 | 工作目录文件夹本身；`user/<用户名>/` 下的其他内容（如插件的数据 `<插件名>/`） |
| `.codex` | 对话文件 `sessions/`、`archived_sessions/`，生成的图片 `generated_images/`，`log/`，`shell_snapshots/`，`.tmp/`，Windows 沙箱的 `.sandbox/*.log` | 登录 `auth.json`、`config.toml`、`.sqlite` 数据库（Codex 也在其中记录对话）、`skills/`、`tmp/` 等其余一切 |

- 有任务排队或执行中的用户，这一轮不清理其工作目录；只要有任务在执行，这一轮也不清理 `.codex`。
- 链接（符号链接、目录联接）只删链接本身，从不进入它指向的位置；本身是链接的工作目录整个跳过。
- 用户很久没来，再发消息时机器人仍按原对话号续接；Codex 找不到时自动新开对话（见“会话”）。工作目录里的旧文件已经没了，需要的要让 Codex 重新生成。
- 清掉的文件如果还有没送达的投递，该投递标记为失败，不再重试。
- 每个任务自己接收的附件和交付过的文件，在任务结束、投递完成并过了保留期后也会按任务清理：只删任务记录里登记过的文件，且必须在该用户的工作目录内（附件只认 `input/` 里的），不满足就跳过并写日志，不会误删。任务记录（数据库）不清理。
- 有文件被删时日志记一条“已清理超过保留期的数据”（文件数和字节数）。

## 访问控制

`.env` 中：`ALLOWED_TENANTS`（整个企业开放，优先于用户名单，管理员也受限）→ 否则 `ALLOWED_USERS` / `ADMIN_USERS`（Open ID）。三者皆空则拒绝所有任务。`ALLOWED_CHATS` 可额外限制会话。改后重启。

机器人不提供按任务查询或取消的命令，用户只能操作自己的对话。所有任务共享本机权限，没有任何限制，用户之间也没有隔离：Codex 能读写其他用户的工作目录，也能读到 `.env` 和 `.codex/auth.json`（共用的账号凭据）。只对可信内部用户开放。

## 指令

机器人自己只认一个：**`/new`**，和 Codex 自己的 `/new` 一样，忘掉之前的对话，下一条消息开始新对话；如果有任务正在执行或排队，先结束它。必须是单独的 `/new`（不带附件、不带别的文字）。其他以 `/` 开头的消息，包括 `/help`、`/status`，都当作普通文字交给 Codex，机器人不会拦截。没有获得授权的人发任何消息，机器人都会回复他的 Open ID 和租户，管理员据此填入 `.env`。

## 运维

```bat
start.cmd doctor
start.cmd stop                  :: 通过本机令牌接口安全停止，也可 Ctrl+C
start.cmd backup                :: 备份数据库到 data/
start.cmd retry-delivery <任务ID|all>  :: 重试失败的投递，不重跑任务
start.cmd codex login           :: 登录项目自己的 Codex；也可 codex login status、codex logout
```

健康检查 `http://127.0.0.1:8765/health`（`codex` 为 Codex 是否可用；`plugins` 为已装的插件和没装上的；`feishu.state` 为长连接实时状态：connecting、connected、reconnecting、failed），就绪 `/ready`（未就绪 503）。长连接失效时服务会自动重建；Codex 未就绪时每 10 秒重新检查一次（登录后无需重启），就绪后每分钟检查一次登录是否还有效。日志在 `data/logs`，每天每个进程一个文件，保留期见“自动清理”；`.env` 可选 `LOG_LEVEL`。

## 版本

`@openai/codex-sdk` 和 `@openai/codex` 固定同一版本（现为 0.163.0），升级时两个一起改。SDK 以 `codex exec --experimental-json` 的事件为接口，事件类型由 SDK 提供；升级后跑 `npm test` 和 `start.cmd doctor`。

数据库（`data/agent.sqlite`）的版本记在 `user_version` 里，现为 1；版本不是 0（新库）或 1 的库会被拒绝，启动时报错并说明是哪个文件。表结构变化时要同时升版本并写明处理办法，目前没有任何升级路径。

单元测试不能替代实机验收：改动后请用飞书私聊和群聊验证卡片、附件回传，以及重启后继续同一个对话。
